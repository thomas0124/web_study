## なぜWebセキュリティが重要か

Webアプリケーションはインターネット上に公開された瞬間から、世界中の攻撃者の標的になります。

セキュリティ事故が起きると：
- ユーザーの個人情報・クレジットカード情報の漏洩
- サービスの停止・売上の損失
- 企業・ブランドの信頼失墜
- 法的責任（個人情報保護法違反など）

## セキュリティの基本原則

### 最小権限の原則

必要最小限の権限しか与えない：

```javascript
// DBユーザーに必要な権限だけを付与
GRANT SELECT, INSERT ON users TO app_user;
// テーブルのDROPやALTERは不要なので与えない

// APIキーのスコープを絞る
const client = new S3Client({ /* read-only権限のみ */ });
```

### 多層防御（Defense in Depth）

1つの防御が突破されても次の防御が機能するように：

```
インターネット → WAF → ロードバランサー → アプリ → DB
                ↑       ↑              ↑      ↑
              DDoS対策  TLS終端        認証  アクセス制御
```

### フェイルセーフデフォルト

デフォルトを「拒否」にして、明示的に許可する：

```javascript
// 悪い例: デフォルトが許可（誰でもアクセス可能）
if (user.role === "banned") return deny();
// → banの見落としは許可につながる

// 良い例: デフォルトが拒否（明示的に許可）
if (user.role !== "admin") return deny();
// → 許可の見落としは拒否につながる
```

## 攻撃の分類

| カテゴリ | 攻撃例 | 対策 |
|---------|-------|------|
| インジェクション | SQLインジェクション・XSS | 入力検証・エスケープ |
| 認証・認可 | セッションハイジャック・CSRF | 適切な認証実装 |
| データ露出 | 平文パスワード保存 | 暗号化・ハッシュ |
| 設定ミス | デフォルトパスワード・不要な公開 | セキュアデフォルト |
| 依存関係 | 脆弱なライブラリの使用 | 定期的なアップデート |

## セキュリティのテスト

```bash
# 依存パッケージの脆弱性チェック
npm audit
pnpm audit

# 既知の脆弱性データベースで確認
snyk test

# セキュリティヘッダーの確認
curl -I https://example.com
```

<Callout type="warning" title="セキュリティはアドオンではなく設計の一部">
セキュリティは「後から追加するもの」ではなく、設計段階から考えるべきものです。「あとでセキュリティを強化する」という判断は技術的負債を大きく膨らませます。特に認証・認可・入力検証は最初から正しく実装しましょう。
</Callout>

## まとめ

- Webアプリは公開した瞬間から攻撃対象になる
- 最小権限・多層防御・フェイルセーフデフォルトが基本原則
- 攻撃はインジェクション・認証・データ露出・設定ミス・依存関係に分類できる
- `npm audit`で依存パッケージの脆弱性を定期確認する
- セキュリティは設計段階から考える
