## コードレビューの目的

コードレビューは「バグを見つける」だけが目的ではありません：

1. **品質の向上**: バグ・セキュリティ問題・パフォーマンス問題の早期発見
2. **知識の共有**: チームメンバーがコードベースを理解する
3. **メンタリング**: 経験者が若いメンバーに知識を伝える
4. **設計の改善**: 別の視点でアーキテクチャの問題を発見する
5. **コードの一貫性**: チームのコーディングスタイルを統一する

## レビュアーとしての心得

### チェックリスト

```markdown
## 機能・ロジック
□ 仕様を満たしているか
□ エッジケースを考慮しているか
□ エラーハンドリングが適切か

## セキュリティ
□ 入力値を検証しているか
□ SQLインジェクション・XSSの可能性はないか
□ 機密情報がコードに含まれていないか

## パフォーマンス
□ N+1クエリが発生していないか
□ 不要な再描画・再計算はないか
□ 大量データの処理でメモリが問題にならないか

## コード品質
□ 関数・変数の命名が分かりやすいか
□ 1つの関数が1つの責任を持っているか
□ コメントがないと理解できない箇所はないか

## テスト
□ 変更に対応したテストがあるか
□ 境界値のテストがあるか
```

### 良いレビューコメントの書き方

```markdown
# 原則: 「コード」を批評する、「人」を批評しない

# ❌ 悪い例
このコードひどいですね。なぜこんな書き方をしたんですか？

# ✅ 良い例（提案の理由を説明）
この実装では毎回DBクエリが発生してN+1問題になる可能性があります。
`include: { posts: true }`でJOINに変えてみてはいかがでしょうか？

# 種類を明示する
[必須] セキュリティ: このクエリはSQLインジェクションの脆弱性があります。
[提案] パフォーマンス: ここはメモ化することで再計算を減らせます。
[質問] この条件式の意図を教えていただけますか？
[称賛] このエラーハンドリングのパターン、とても参考になりました！
```

## レビューを受ける側の心得

```markdown
1. フィードバックをパーソナルに受け取らない
   → コードへのフィードバックであり、あなたへの批判ではない

2. 「なぜ」を質問する
   → 「なぜそうすべきか分からない」は質問していい

3. 変更に感謝する
   → レビュアーはあなたのコードの改善のために時間を割いている

4. 全コメントに返答する
   → 対応済み: "Done" / 議論したい: 理由を説明

5. 小さなPRを作る
   → レビューしやすいPRは400行以下が目安
```

## 自動化でレビュー負荷を減らす

```yaml
# .github/workflows/ci.yml
- name: Lint
  run: pnpm eslint .  # スタイルはCIに任せる

- name: Type check
  run: pnpm tsc --noEmit

- name: Test
  run: pnpm test
```

```javascript
// .eslintrc.cjs
module.exports = {
  rules: {
    // よくあるバグを自動検出
    "no-unused-vars": "error",
    "eqeqeq": "error",       // ===を強制
    "no-console": "warn",    // console.logの残留を警告
  },
};
```

<Callout type="tip" title="レビューの時間を決める">
レビューが溜まるとPRがブロックされてチームの開発速度が落ちます。「作業開始時と午後に各30分」などレビューの時間をカレンダーに入れておくことで、レビューを滞留させないチームリズムが作れます。
</Callout>

## まとめ

- コードレビューは品質向上・知識共有・メンタリングが目的
- セキュリティ・パフォーマンス・コード品質・テストを確認する
- コメントは「コード」を批評し、理由と提案をセットで書く
- レビューを受ける側はフィードバックをパーソナルに受け取らない
- ESLint・型チェック・テストを自動化してレビューの負荷を下げる
